jq one-liners for cleaning messy JSON logs

If you've ever stared at a wall of minified JSON logs trying to find one field, you know the pain. jq turns that chaos into something workable in seconds. Here are the one-liners I actually use when cleaning and triaging messy log data — no wrappers, no scripts, just raw shell commands you can paste and run.

The Basics You Probably Already Know (but let's be sure)

Pretty-printing is the entry point. If your logs are one giant blob per line:

cat app.log | jq '.'

That's table stakes. The real value starts when you're filtering, reshaping, and stripping noise out of logs that someone else designed at 2am.

Extracting Specific Fields Across Every Line

Log files typically have one JSON object per line. Pull just the fields you care about:

jq '{timestamp: .ts, level: .severity, msg: .message}' app.log

This remaps ugly internal field names to something readable. Pair it with -c to keep output compact (one line per entry), which is useful if you're piping downstream:

jq -c '{timestamp: .ts, level: .severity, msg: .message}' app.log

Filtering Out the Noise

Skip low-level log entries

If your logs are flooded with DEBUG lines while you're hunting an error:

jq 'select(.level == "ERROR" or .level == "WARN")' app.log

select() is your best friend here. It passes through only the objects where the condition is true, dropping everything else silently.

Filter by time range

Logs from a specific window, assuming ISO timestamps:

jq 'select(.timestamp >= "2024-11-01T10:00:00" and .timestamp <= "2024-11-01T11:00:00")' app.log

This works because ISO 8601 strings sort lexicographically. Not perfect for every timestamp format, but covers most structured log setups.

Dealing with Missing or Null Fields

Real logs are inconsistent. Some entries have a user_id, some don't. Trying to extract it blindly will give you a bunch of null values. Fix that:

jq 'select(.user_id != null) | .user_id' app.log

Or use the alternative operator to provide a fallback:

jq '.user_id // "anonymous"' app.log

The // operator returns the right side when the left is null or false. Huge for normalizing logs before sending them somewhere else.

Flattening Nested Garbage

Some logging libraries nest everything. You end up with structures like .context.request.headers.x-trace-id. Flatten what you need:

jq '{trace_id: .context.request.headers["x-trace-id"], status: .context.response.status}' app.log

If the nesting is truly arbitrary and you just want every key-value pair at one level:

jq '[leaf_paths as $p | {key: ($p | join(".")), value: getpath($p)}] | from_entries' app.log

That one's heavier, but it fully flattens any object into a single-depth map with dotted key names. Useful when you're dumping into a CSV or a key-value store.

Counting and Summarizing

Quick frequency count of log levels across the whole file:

jq -r '.level' app.log | sort | uniq -c | sort -rn

Yes, that's cheating by falling back to shell tools — but it's the practical move. jq handles the extraction, Unix handles the aggregation.

If you want to stay purely in jq, slurp the file and group:

jq -s 'group_by(.level) | map({level: .[0].level, count: length})' app.log

The -s flag slurps all lines into a single array, then group_by does the rest. Watch memory usage on large files though.

Stripping Fields You Don't Want

Sometimes you're sending logs somewhere and need to drop sensitive or irrelevant fields before forwarding:

jq 'del(.password, .auth_token, .internal_debug)' app.log

del() removes keys in place. Chain multiple fields in one call. Works on nested paths too: del(.user.ssn).

Handling Broken Lines

Logs in the wild often have non-JSON lines mixed in — startup banners, stack traces, whatever. By default jq will just error and stop. Use this instead:

jq -R 'fromjson? | select(type == "object")' app.log

-R reads each line as a raw string, fromjson? tries to parse it and suppresses errors, and select(type == "object") keeps only valid JSON objects. This combo handles garbage lines without babysitting the process.

Putting It Together

A realistic end-to-end example: grab all ERROR logs from the last hour, drop internal fields, and write clean compact JSON to a new file:

jq -Rc 'fromjson? | select(type == "object") | select(.level == "ERROR") | select(.timestamp >= "2024-11-01T09:00:00") | del(.internal, .debug_ctx)' app.log > errors_clean.log

That's one line doing parse-guarding, filtering, time scoping, and field removal all at once. No temp files, no intermediate scripts.

jq rewards spending 20 minutes with its manual. The patterns above cover 80% of log-cleaning work, but once you're comfortable with select, del, and the ? error suppression operator, you'll start reaching for it before anything else when logs get messy.
